# v0.1.0-beta.32

Diese Version vereinfacht den MCP-Standardweg: Das Paket
`@yadimon/steuer-spar-erklaerung-mcp` besitzt jetzt eine normale, exakte
Dependency auf dieselbe Releaseversion von
`@yadimon/steuer-spar-erklaerung-api`. npm installiert die passende API
automatisch. Es gibt kein `postinstall` und keine Installation zur Laufzeit.
Unterstützt bleibt SteuerSparErklärung 2025 mit Engine-Major 31.

ELSTER und jede andere Übermittlung ans Finanzamt bleiben gesperrt. Ebenso
unverändert bleiben das Verbot automatischen Speicherns und die Bindung jeder
Steuerfallbearbeitung an einen eindeutig bestätigten Fall.

## Lokaler API-Singleton

Vor dem MCP-stdio-Handshake und bei `--selftest` prüft der Server zuerst die
konfigurierte Loopback-Adresse. Eine bereits laufende API wird nur übernommen,
wenn `/healthz` den erwarteten Paketnamen, dieselbe exakte Paketversion, die
passende API-Version, eine gültige Prozess-/Instanz-ID und einen gültigen
pfadfreien Konfigurationsfingerprint meldet. Bei einer von MCP verwalteten
Konfiguration muss der Fingerprint exakt zur erwarteten Ressourcenbindung
passen; bei autoritativem `SSE_API_URL` ist kein lokaler Sollwert bekannt. MCP
wiederholt diese Identitätsprüfung vor jedem späteren API-Aufruf und bindet den
anschließenden POST an dieselbe Instanz-ID.

Ist am Standardziel keine API erreichbar, startet MCP seine installierte
Dependency unsichtbar und mit vollständig getrenntem stdio, wartet auf
Readiness und verwendet sie anschließend. Zwei parallele MCP-Starts
konvergieren über das Port-Rennen auf eine API. Der Verlierer übernimmt die
inzwischen bereite kompatible Instanz; die API darf nach dem Ende des Clients
für den nächsten Start weiterlaufen.

Ein fremder Dienst, eine unvollständige Identität oder eine abweichende
Releaseversion führt redigiert und fail-closed zum Startabbruch. Die Produktion
beendet niemals Prozesse anhand eines Namens oder nach einem verlorenen Rennen.
Eine ausdrücklich gesetzte `SSE_API_URL` bleibt autoritativ: Ist sie nicht
erreichbar und kompatibel, gibt es weder Fallback noch Autostart am
Standardport. Ein absoluter `SSE_API_CONFIG`-Pfad wählt optional einen eigenen
Arbeitsbereich; ohne ihn gelten die sicheren Vorgaben unter `%LOCALAPPDATA%`.

## Distribution und Plattform

Weil MCP nun exakt vom Windows-nativen API-Paket abhängt, sind beide npm-Pakete
ausdrücklich auf Windows x64 begrenzt. Der Publish-Workflow veröffentlicht die
API vor dem davon abhängigen MCP-Paket. Die API bleibt unabhängig davon für
direkte HTTP-/CLI-Nutzung separat installierbar.

## Dokumentation und Verifikation

README, Installation, beide Paket-READMEs, Architektur, Verifikation,
Runtime-Skill und öffentlicher Post beschreiben jetzt denselben Standardweg:
MCP installieren, Client eintragen, einmal neu starten — kein dauerhaft
offenes API-Terminal.

Der Release-Prozess prüft alle 136 geplanten Schritte, darunter 127 parallele Haupttests
mit konfliktbewusster Worker-Serialisierung und drei exklusive
Windows-Prozess-/Packaging-Gates. Neu belegt sind Autostart und Readiness,
Wiederverwendung, paralleler Erststart, fremder Portinhaber, Versionsabweichung,
abweichende Konfiguration, Prozesswechsel nach dem Handshake, ein eigener Port
im Default-Config, autoritative unerreichbare URL, protokollreines MCP-stdout,
unsichtbarer Start und Clean-install nur des MCP-Pakets mit automatisch
installierter exakter API.

Für `launch` gilt weiterhin eine gemeinsame Kaltstartfrist von 240 Sekunden
für CLI und MCP-Tool `sse_launch`; das allgemeine MCP-Toolbudget bleibt 300
Sekunden.
