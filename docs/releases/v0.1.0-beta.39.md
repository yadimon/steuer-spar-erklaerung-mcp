# v0.1.0-beta.39

SteuerSparErklärung 2025 mit Engine-Major 31 bleibt das unterstützte
Produktprofil. ELSTER und jede andere Übermittlung ans Finanzamt bleiben
gesperrt. Ebenso unverändert bleiben das Verbot automatischen Speicherns, die
Bindung an einen eindeutig bestätigten Fall, die private hashverifizierte
Sicherung vor dirty-fähiger Bedienung und der unmittelbare Readback jeder
Änderung.

Diese Version korrigiert eine irreführende Stelle in der Hilfe der CLI. Am
Verhalten der API und des Workers ändert sich nichts.

## Die Hilfe verschwieg einen Unterschied zwischen den PowerShell-Editionen

Seit `beta.38` nimmt `steuer-spar-erklaerung-call` Argumente direkt in der
Kommandozeile entgegen. Ein Wert wird als JSON gelesen, wenn er sich als JSON
lesen lässt — `--hwnd 123` ergibt also eine Zahl. Für eine Zeichenkette, die
wie eine Zahl aussieht, nannte die Hilfe die Schreibweise `--name '"2024"'`.

Diese Angabe war für die häufigste Umgebung falsch. Nachgemessen auf derselben
Maschine mit einem Programm, das nur seine Argumente ausgibt:

| Schreibweise | Windows PowerShell 5.1 | PowerShell 7 |
|---|---|---|
| `--pageId '"2024"'` | `2024` — Anführungszeichen entfernt | `"2024"` — durchgereicht |
| `--pageId '\"2024\"'` | `"2024"` — richtig | `\"2024\"` — unbrauchbar |

Die beiden Editionen übergeben native Argumente gegensätzlich, und **es gibt
keine Schreibweise, die in beiden funktioniert**. Das dokumentierte Beispiel
wirkte ausgerechnet unter Windows PowerShell 5.1 nicht — der Edition, unter der
dieses Projekt seinen Worker ausführt.

Unangenehm daran ist der stille Fall: Statt der Zeichenkette kommt eine Zahl
an, ohne dass die Shell etwas meldet. Bei `pageId` fängt das Schema es mit
`Expected string, received number` ab; bei einem Feld, das beide Typen
zulässt, wäre es unbemerkt geblieben.

Hilfe und `docs/API-MCP-VERTRAG.md` benennen den Unterschied jetzt und
verweisen für erzwungene Typen auf `--args-file`, das ohne Shell-Quotierung
auskommt. Es wurde bewusst **keine neue Syntax** eingeführt — der verlässliche
Weg existierte bereits.

Gefunden wurde das beim Nachtesten des veröffentlichten `beta.38` auf einer
frischen Windows-VM. Auf dem Entwicklungsrechner war es nicht zu sehen, weil
dort PowerShell 7 läuft.

## Zeitgrenzen

Für CLI und MCP-Tool `sse_launch` gilt unverändert eine gemeinsame
Kaltstartfrist von 240 Sekunden; die übrigen Toolbudgets und alle dauerhaften
Sicherheitsgrenzen bleiben operationsspezifisch. Unbekannte Versionen und
unklare Ressourcenbindungen bleiben fail-closed.

## Verifikation vor Veröffentlichung

Der vollständig bestandene Suite-Plan umfasst alle 159 geplanten Schritte,
darunter 146 parallele Haupttests mit konfliktbewusster Worker-Serialisierung
und vier exklusive Windows-Prozess-/Packaging-Gates. Der Operationskatalog
bleibt bei 100 Operationen; das Produktprofil bleibt auf Build `31.0.2.0`
nachverifiziert.

Das veröffentlichte `beta.38` wurde zusätzlich auf einer Windows-VM ohne
Entwicklungsumgebung geprüft: Installation aus der Registry unter Node 24,
beide Pakete auf der erwarteten Version, alle drei CLI-Einstiege lauffähig, und
über einen selbst gestarteten API-Server auch der volle Weg eines
Kommandozeilenarguments bis in die Operation.

## Weiterhin offen

Ein Testfall meldet unter Last gelegentlich `ECONNRESET` statt der
spezifischeren Meldung, dass der API-Prozess ausgetauscht wurde. Der Aufruf
bleibt dabei fail-closed; verloren geht nur der Hinweis, dass der MCP-Server
neu zu starten ist. Die Ursache ist bekannt und noch nicht behoben.
