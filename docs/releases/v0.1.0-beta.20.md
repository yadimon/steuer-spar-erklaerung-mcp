# v0.1.0-beta.20

Diese Version behebt sechs Fehler, die erst ein vollständiger Lauf in einer
sauberen Windows-VM zeigte — vom ersten `npm i` bis zum geschützten
Feldschreibvorgang. Zwei davon machten je eine dokumentierte Kernfunktion
unbenutzbar. Am Umfang ändert sich nichts: dieselbe lokale API, derselbe
MCP-Wrapper, dieselben 88 Operationen für SteuerSparErklärung 2025. ELSTER und
jede andere Übermittlung ans Finanzamt bleiben gesperrt.

## `collect` war über die API gar nicht benutzbar

`collect` ist der Weg, eine ganze Seitenstrecke am Stück zu lesen. Erfasste ein
Segment genau **eine** Seite — der Normalfall am Ende eines Blätterpfads —,
antwortete die API mit `invalid-operation-result` statt mit dem Ergebnis.

Ursache war ein PowerShell-Fallstrick: Das Seitenfeld entstand in einem
`$(...)`-Unterausdruck, und der gibt genau ein Element als Objekt statt als
Liste zurück. Der Ergebnisvertrag verlangt eine Liste und wies die Antwort ab.

Der Ergebnisvertrags-Wächter prüft diese Klasse jetzt für **jedes** Listenfeld
aller Worker-Operationen, nicht nur für die eine Stelle.

## Der einzige erlaubte Schreibweg für Steuerfelder scheiterte

Steuerfelder werden ausschließlich über `tracked_set_value` geändert, und die
Operation vergleicht dabei die Ergebniswerte vor und nach der Änderung. Dafür
muss die Werte-Info offen sein.

Zwei Fehler standen dem im Weg:

- Nach dem Öffnen wurde **einmal fest** 700 bzw. 900 ms gewartet und dann genau
  einmal nachgesehen. Auf einer langsameren Maschine war das zu kurz; die
  Operation brach mit „Werte-Info nicht eindeutig (0 Fenster)" ab. Lesen und
  Schreiben teilen sich jetzt einen Helfer, der auf das Fenster **wartet**.
- Deckte die Werte-Info ausgerechnet das Zielfeld ab, brach die
  Mutationsepoche mit `epoch-obstructed` ab und meldete „fremde Eingabe" —
  obwohl niemand eingegriffen hatte. Auflösen konnte das niemand: Eine
  Operation zum Verschieben von Fenstern gibt es bewusst nicht. Die Operation
  räumt ihr eigenes Hilfsfenster jetzt **vor** der Mutationsepoche aus dem Weg
  und weist das in `ergebnisFensterVerschoben` aus. Die Epoche selbst bleibt
  unverändert prüfungspflichtig.

## Drei Meldungen, die etwas Falsches behaupteten

- `health` meldete ohne laufendes Programm `buildDrift.drifted=true`, weil ein
  leerer Prozess-Build in den Vergleich ging. Gemeldet wird jetzt der Build der
  installierten Datei. Der fail-closed-Vergleich selbst bleibt unverändert.
- `close` prüfte genau einmal, ob der Prozess weg ist. SteuerSparErklärung
  braucht länger, also kam ein Fehlschlag zurück, obwohl das Programm Sekunden
  später regulär beendet war. Jetzt wird bis zu 20 s gewartet und sofort
  geantwortet, sobald der Prozess weg ist.
- `get_value` mit einer Feldbeschriftung lieferte die Beschriftung und damit
  `value=null`, während `sse_change_field` unter **demselben** Namen das
  zugehörige Eingabefeld beschrieb. Wer erst liest und dann schreibt, bekam
  zwei verschiedene Dinge. `get_value` benutzt jetzt dieselbe Zuordnung und
  weist in `aufgeloestUeber` aus, welcher Weg gegriffen hat.

## Erste Operation, erste Enttäuschung

`launch` startet ein fremdes Programm und wartet, bis es bedienbar ist. Auf
einem kalten Rechner gemessen: **96 Sekunden**. Die allgemeine Vorgabe von 90
Sekunden ließ damit ausgerechnet die erste Operation scheitern, die ein Nutzer
aufruft. Frist und Begründung stehen jetzt an einer Stelle im Vertrag:
**240 Sekunden**, gleich für die CLI und für das MCP-Tool `sse_launch`. Damit
entfällt der bisherige Unterschied zwischen beiden Transporten. Die Operation
antwortet, sobald das Fenster bereit ist; die größere Frist kostet im
Erfolgsfall nichts, und `--timeout-ms` überschreibt sie weiterhin.

## Ein falscher Name kostet keine Extrarunde mehr

Ein falsch geratener Argumentname war eine Sackgasse: Die Meldung nannte den
falschen Namen, aber nicht die richtigen. Jetzt listet sie die erlaubten Namen
der Operation gleich mit, über Union-Zweige hinweg und an beiden Grenzen (API
und MCP):

```text
Unrecognized key(s) in object: 'discardUnsaved'.
Erlaubt sind: discardChanges, force, hwnd, pid, save
```

Wertfehler ohne unbekanntes Feld bleiben unverändert knapp.

## Anleitung

Das Ordnerbild nannte nur `.agents\skills`. Nachgemessen: Bei
`--agent claude-code` legt der Skill-Installer `.claude\skills` an, bei
`--agent codex` `.agents\skills`. Der Ordner enthält bei Claude Code außerdem
`.mcp.json`.

## Unveränderte Grenzen

- Es läuft immer nur eine Operation je API; ein zweiter Aufruf wird sofort mit
  HTTP 409 und `code: "busy"` abgelehnt.
- MCP bleibt ein optionaler, PC-blinder Wrapper über die lokale Loopback-API;
  dieselben Operationen bleiben über die lokale CLI verfügbar.
- Noch nie erfolgreich live belegt sind die sechs VaSt-Wege `vast_apply`,
  `vast_dialog_read`, `vast_mapping_options`, `vast_mapping_select`,
  `vast_row_details` und `vast_row_set_expanded`.

## Verifikation

Der vollständige Offline-Releaseplan umfasst alle 119 geplanten Schritte,
davon 112 konfliktfreie Haupttests, und bleibt grün. Zusätzlich lief in einer
sauberen Windows-11-VM der gesamte dokumentierte Installationsweg wörtlich
durch, gefolgt von Lese-, Schreib- und MCP-Läufen gegen einen offiziellen
Musterfall auf einer hashverifizierten Arbeitskopie. Dabei wurde `instances`
zum ersten Mal mit einer laufenden Instanz live belegt; der Evidenzkatalog
führt die Operation weiterhin als ungetestet, weil er nur aus aufgezeichneten
Suite-Läufen wächst. Details und Messwerte stehen in `docs/VERIFIKATION.md`.

Nicht geprüft: ein echter Agentenlauf in der VM — Claude Code war dort
installierbar, aber nicht angemeldet.

Unverändert gilt: nur Windows x64, nur SteuerSparErklärung 2025 mit
Engine-Major 31, Node.js 22 oder neuer mit npm.
