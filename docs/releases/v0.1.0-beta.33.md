# v0.1.0-beta.33

> **Entwurf:** Diese Notes beschreiben den geplanten Agent-Plugin-1.0-Release.
> Die Online-Kaltphase der sauberen VM-Matrix ist belegt; die Offline-MCP-Phase
> bleibt ausdrücklich offen. Daraus wird hier noch kein vollständig bestandener
> Nutzerweg behauptet. Es erfolgten weder Publish noch Tag oder GitHub Release.

SteuerSparErklärung 2025 mit Engine-Major 31 bleibt das unterstützte
Produktprofil. ELSTER und jede andere Übermittlung ans Finanzamt bleiben
gesperrt. Ebenso unverändert bleiben das Verbot automatischen Speicherns, die
Bindung an einen eindeutig bestätigten Fall, die private hashverifizierte
Sicherung vor dirty-fähiger Bedienung und der unmittelbare Readback jeder
Änderung.

## Agent Plugin 1.0

Der primäre Nutzerweg wird ein universell installierbares Agent Plugin für
Codex und Claude Code. Es bündelt versionsgleich:

- den Skill `steuer-spar-erklaerung`;
- MCP und lokale API;
- PowerShell-/Native-Runtime und Produktprofile;
- alle JavaScript-Dependencies und Hilfsassets.

Das generierte `mcp.json` startet Node direkt aus `${PLUGIN_ROOT}`. Im
Auftragsordner ist kein `node_modules` nötig; beim MCP-Start laufen weder npm
noch npx und es erfolgt kein Netzwerkdownload. Der bestehende standalone
npm-Weg für API oder MCP bleibt als fortgeschrittener Einstieg verfügbar.

Root-Manifest, MCP-Manifest und target-spezifische Kompatibilitätsmanifeste
werden aus einer gemeinsamen Release-Metadatenquelle erzeugt. Release-Gates
prüfen, dass Plugin, MCP-npm-Paket, API-npm-Paket und Runtime dieselbe exakte
Version tragen.

## Installation und First run

Der dokumentierte Quickstart nennt das Ziel ausdrücklich als `codex` oder
`claude-code`; automatische Target-Erkennung ist unter Windows nicht der
Hauptweg. Der einmalige Installer benötigt Git auf `PATH`, weil
`plugins@1.3.4` das Plugin-Repository klont; danach bleibt Node.js 22+ die
einzige zusätzliche Runtime. `plugins@1.3.4` ignoriert den
Scope bei Codex und schreibt bei beiden Zielen trotz `--scope project` in
clientverwaltete Benutzer-Caches/config. Diese Grenze ist offen dokumentiert:
Der Flag ist keine physische Projektisolation. Auftragskontext und bei Bedarf
ein eigener absoluter `SSE_API_CONFIG`-Pfad sorgen für die tatsächliche
Trennung.

Die Codex-Installation ist derzeit zweistufig: Nach
`plugins@1 add ... --target codex --scope project --yes` ist zusätzlich
`codex plugin add steuer-spar-erklaerung@plugins-cli --json` erforderlich. Ein
isolierter Lauf mit `plugins@1.3.4` und Codex CLI 0.151 zeigte nach dem ersten
Schritt noch `not installed` und erst nach dem target-nativen zweiten Schritt
`installed, enabled` für v0.1.0-beta.33. Bei Claude Code genügte der einzelne
`plugins@1 add ... --target claude-code --scope project --yes`-Aufruf, um den
Eintrag als `enabled` zu registrieren. Diese Client-Evidenz belegt den
Registrierungsvertrag. Die spätere VM-Online-Kaltphase bestätigt beide
Zielinstallationen; die vollständige Matrix bleibt wegen der Offline-Phase
offen.

Der neue First-run-Wizard merkt sich den ursprünglichen Auftrag, ruft
`sse_preflight` auf, stellt höchstens eine Frage pro Nachricht, bevorzugt den
bereits eindeutig geöffneten Fall und lässt andernfalls Fall plus vollständige
Belegquellen bestätigen. Nach einem gemeinsam bestätigten sicheren Plan setzt
er den ursprünglichen Auftrag fort. Er installiert nichts als versteckte
Standardaktion.

## Singleton und Sicherheit

Der MCP-Supervisor übernimmt weiterhin nur eine exakt passende API-Identität
oder startet die mitgelieferte API unsichtbar. Fremde Portinhaber, alte
Versionen und unklare Ressourcenbindungen bleiben fail-closed; Produktion und
Entfernungsanleitung verwenden keine Prozessname-Sweeps.

Für CLI und MCP-Tool `sse_launch` gilt eine gemeinsame Kaltstartfrist von 120
Sekunden. Die übrigen Toolbudgets und alle dauerhaften Sicherheitsgrenzen
bleiben operationsspezifisch.

## Verifikation vor Veröffentlichung

Der aktuelle Suite-Plan umfasst alle 144 geplanten Schritte, darunter 133
parallele Haupttests mit konfliktbewusster Worker-Serialisierung und vier
exklusive Windows-Prozess-/Packaging-Gates. Diese Zahlen sind vor dem Release
gegen `test/suite-plan.mjs` zu aktualisieren, falls sich der Plan ändert.

Eine unabhängige vollständige Windows-11-x64-VM-Kopie ohne Shared Folder und
ohne übertragene Credentials bestand die Online-Kaltphase mit dem
hashgebundenen Auditarchiv `3ee62c...419d3`. Für v0.1.0-beta.33 und
`plugins@1.3.4` liefen je zwei Codex- und Claude-Code-Installationen durch:
Codex jeweils mit dem notwendigen target-nativen zweiten Schritt, Claude Code
einstufig. Die wiederholten Installationen lieferten stabile Belege; die
Abschlussinventur fand keine verbliebenen Runtime-/Auditprozesse und keine
Credential-Dateien.

Die Offline-MCP-Phase ist weiterhin Pflicht und offen. Drei reproduzierbare
rote Befunde wurden bereits korrigiert: sechs nicht gelockte Fixture-Dateien
im ausgelieferten Runtimebaum wurden aus dem Produkt-Build entfernt, der
Selftest-Harness akzeptiert jetzt Pretty-JSON statt fälschlich genau einer
Ausgabezeile, und `tools/call` verwendet den etablierten 300-Sekunden-
MCP-Vertrag statt 180 Sekunden. Ein späterer `sse_preflight`-MCP-Fehler konnte
nicht mehr inhaltlich erfasst werden, weil die VM extern pausiert wurde und
VirtualBox per RPC abbrach. Danach blockierte das WSL-Backend des VM-Laufwerks
mit `CreateInstance` `0x800705b4` beziehungsweise `VERR_WRITE_PROTECT`; ohne
administrative Rechte war kein Backend-Neustart möglich. Dieser
Infrastrukturblocker ist kein Offline-Erfolg und keine Klassifikation des
MCP-Fehlers.

Bis zum vollständigen Offline-Readback bleiben außerdem API-Autostart ohne
weitere Installation, Update über zwei Versionen, target-native/manuelle
Entfernung, kein npm/npx/Netzwerk beim MCP-Start, protokollreines stdout sowie
Singleton-/Portkonflikte in der VM offen. OpenCode gehört nicht zu dieser
Release-Matrix. v0.1.0-beta.33 bleibt ein Entwurf; Publish, Tag und GitHub
Release sind nicht erfolgt.
